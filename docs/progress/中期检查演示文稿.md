## 幻灯片 4：系统总体架构

标题：系统总体架构

页面内容：

```text
客户端
  -> /move_joints Action
motion_api_node
  -> /motion_command
planner_node
  -> /planned_traj
controller_node
  -> /joint_cmd
robot_interface_node
  -> /joint_trajectory_controller/joint_trajectory
Gazebo / ros2_control
  -> /joint_states
```

讲解词：

这是当前系统的主运动链路。外部客户端通过 `/move_joints` Action 发送运动目标。`motion_api_node` 作为任务入口，负责校验参数并生成内部运动命令。`planner_node` 根据当前关节状态和目标关节角生成规划轨迹。`controller_node` 按轨迹点输出控制命令。`robot_interface_node` 将上层命令转换为 Gazebo 控制器可识别的 `JointTrajectory`。最后，Gazebo 通过 `/joint_states` 发布关节状态反馈，供规划和控制模块使用。

## 幻灯片 5：功能包划分

标题：ROS2 功能包划分

页面内容：

- `robot_motion_msgs`：自定义 msg、action、srv 接口。
- `motion_api_pkg`：运动任务 Action 入口。
- `planner_pkg`：关节空间轨迹规划。
- `controller_pkg`：轨迹执行与到位判定。
- `robot_interface_pkg`：Gazebo/ros2_control 接口适配。
- `system_manager_pkg`：任务状态、系统状态、reset 和异常管理。
- `bringup_pkg`：统一启动入口。
- `robot_common_pkg`：公共常量和状态语义。

讲解词：

系统按照功能职责划分为多个 ROS2 包。接口定义集中在 `robot_motion_msgs`，任务入口、规划、控制、接口适配和系统管理分别由独立功能包实现。这样划分的好处是模块边界清晰，便于后续扩展，也便于在论文中说明系统设计。

## 幻灯片 6：状态管理设计

标题：状态管理设计

页面内容：

```text
业务节点
  -> /motion_event
system_manager_node
  -> /task_state
  -> /system_state
```

- `/motion_event`：业务节点上报事件。
- `/task_state`：正式任务状态。
- `/system_state`：系统整体状态。
- 正常任务流转：`accepted -> planning -> executing -> completed`
- 异常状态：`failed`、`rejected`、`canceled`

讲解词：

系统状态管理采用“事件流 + 正式状态流”的方式。业务节点只负责发布发生了什么事件，例如任务接收、规划开始、规划完成、执行开始和执行完成。`system_manager_node` 根据事件和状态机规则统一发布正式任务状态和系统状态。这样可以避免多个节点各自发布状态导致语义混乱，也让任务生命周期更容易观察和调试。
