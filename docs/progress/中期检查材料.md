# 毕业设计中期检查材料

## 一、课题基本情况

课题名称：基于 ROS2 的工业机器人运动控制系统架构设计与仿真验证

本课题面向 UR5 工业机器人仿真场景，基于 Ubuntu 22.04、ROS2 Humble 和 Gazebo 平台，设计并实现一套分层式工业机器人运动控制系统。系统以 ROS2 多节点通信为基础，围绕“任务接收、运动规划、控制执行、机器人接口适配、系统状态管理、仿真验证”构建完整软件架构。课题重点不是复杂控制算法推导，而是完成一个结构清晰、接口明确、可运行、可验证的运动控制系统原型，并通过 Gazebo 仿真验证系统功能和工程可行性。

当前毕业设计已经完成选题确认、技术路线规划、开发环境搭建、最小运动控制验证、系统工程结构搭建和核心功能链路实现。系统已经具备从 Action 任务输入到轨迹规划、轨迹执行、底层仿真控制器适配、状态反馈和异常处理的基本闭环能力。下一阶段工作重点是完善系统化实验验证、补充实验数据分析、进一步整理文档并开展论文撰写。

## 二、当前工作进度

### 1. 选题与技术路线已经确定

前期已经完成毕业设计题目确定，明确课题名称为“基于 ROS2 的工业机器人运动控制系统架构设计与仿真验证”。结合计算机科学与技术专业背景，本课题将研究重点放在 ROS2 机器人软件架构设计、运动控制流程组织、系统状态管理和仿真验证上。

已确定的技术路线如下：

- 操作系统采用 Ubuntu 22.04 LTS。
- 机器人开发框架采用 ROS2 Humble。
- 主要开发语言采用 C++。
- 仿真平台采用 Gazebo。
- 机器人对象采用 UR5 工业机器人。
- 系统通信方式采用 ROS2 topic、action 和 service。
- 运动任务入口采用自定义 Action 接口 `/move_joints`。
- 系统验证方式采用 Gazebo 仿真、ROS2 topic 观察、rosbag 数据记录和运行脚本测试。

本阶段已经明确了课题边界：系统侧重于运动控制软件架构与流程验证，不涉及真实机械臂硬件部署，也不以高精度动力学建模和复杂控制算法为主要研究内容。

### 2. ROS2 与 Gazebo 开发环境已经搭建完成

目前已完成 ROS2 Humble 开发环境和 Gazebo 仿真环境配置，并完成了基础功能验证。通过 ROS2 命令行工具能够正常查看节点、话题和接口；Gazebo 能够启动 UR5 机器人模型，并能发布 `/joint_states` 等关节状态信息。

在最小系统验证阶段，已经确认 UR5 模型可以在 Gazebo 中正常加载，机器人关节名称、关节数量和控制接口能够与 ROS2 系统对接。通过简单控制命令可以驱动机器人产生运动，为后续自行设计运动控制系统提供了可用的仿真基础。

### 3. ROS2 工程结构已经建立

当前已经建立正式毕业设计工作空间，工程目录结构较完整。项目主要包括源码、架构文档、接口文档、实验文档、进度文档、测试脚本和 rosbag 数据目录。

当前 ROS2 功能包划分如下：

- `robot_motion_msgs`：统一定义自定义消息、Action 和 Service 接口。
- `motion_api_pkg`：提供运动任务 Action 入口，负责接收任务、校验参数、生成任务编号并下发内部命令。
- `planner_pkg`：负责根据目标关节角和当前关节状态生成规划轨迹。
- `controller_pkg`：负责接收规划轨迹，按固定频率分步下发控制命令，并进行执行状态判定。
- `robot_interface_pkg`：负责将上层控制命令转换为 Gazebo/ros2_control 可识别的 JointTrajectory 指令。
- `system_manager_pkg`：负责系统状态、任务状态、异常事件、超时和 reset 管理。
- `bringup_pkg`：负责统一启动系统节点、仿真环境和 RViz 配置。
- `robot_common_pkg`：负责维护跨包共享常量、状态字符串和事件语义。

这种功能包划分使系统具有较清晰的层次结构，各模块职责边界明确，方便后续扩展和论文说明。

### 4. 系统总体架构已经实现

当前系统已经按照“任务入口层、规划层、控制执行层、机器人接口层、系统管理层”的分层思想完成基本实现。

主运动链路如下：

```text
客户端
  -> /move_joints Action
motion_api_node
  -> /motion_command
planner_node
  -> /planned_traj
controller_node
  -> /joint_cmd
robot_interface_node
  -> /joint_trajectory_controller/joint_trajectory
Gazebo / ros2_control
  -> /joint_states
```

状态管理链路如下：

```text
motion_api_node / planner_node / controller_node / robot_interface_node
  -> /motion_event
system_manager_node
  -> /task_state
  -> /system_state
```

其中，主运动链路负责机器人运动任务从输入到执行的流程，状态管理链路负责统一收敛任务状态和系统状态。该设计避免了各业务节点直接对外发布混乱状态，使系统状态语义更加统一。

### 5. 自定义接口已经完成

当前已经完成系统所需自定义接口定义，包括：

- `MoveJoints.action`：用于接收关节运动任务，支持目标关节名、目标关节角、速度缩放和超时参数。
- `MotionCommand.msg`：用于系统内部传递运动命令和关节目标。
- `PlannedTrajectory.msg`：用于传递规划后的关节轨迹。
- `MotionEvent.msg`：用于各业务模块上报任务事件。
- `TaskState.msg`：用于发布正式任务状态。
- `SystemState.msg`：用于发布系统整体状态。
- `ResetSystem.srv`：用于系统复位。

接口文档已经在 `docs/interfaces/` 下进行整理，便于后续论文中描述系统通信机制，也方便答辩时展示系统接口设计。

### 6. 运动任务入口模块已经实现

`motion_api_pkg` 已经实现 `/move_joints` Action Server。该模块能够接收外部客户端提交的运动任务，并对输入参数进行基本校验，例如关节名数量与目标关节角数量是否一致、速度缩放和超时参数是否有效等。

当前系统采用单任务串行执行策略。当系统中已有活动任务时，新任务会被拒绝，从而避免多个运动任务同时执行造成状态混乱。该策略虽然相对保守，但更适合本科毕业设计阶段的系统稳定性验证，也有利于清晰说明任务生命周期。

该模块还会生成 `task_id`，并将该任务编号贯穿后续规划、控制、事件和状态反馈链路，使任务在系统内部具有可追踪性。

### 7. 运动规划模块已经实现

`planner_pkg` 当前已经实现基于关节空间线性插值的简单轨迹规划器。规划器订阅 `/motion_command` 和 `/joint_states`，根据当前关节位置与目标关节位置生成离散轨迹点，并发布 `/planned_traj`。

当前规划算法主要特点如下：

- 使用当前关节状态作为轨迹起点。
- 使用目标关节角作为轨迹终点。
- 按配置的轨迹点数量进行线性插值。
- 支持 `speed_scale` 速度缩放参数。
- 生成带有时间信息的轨迹点序列。

虽然该规划方法较简单，但具有实现清晰、行为可解释、便于验证的优点，符合本课题以系统架构和控制流程验证为重点的定位。

### 8. 控制执行模块已经实现

`controller_pkg` 已经实现轨迹执行器，能够接收 `/planned_traj`，并按照固定控制频率分步发布 `/joint_cmd`。控制层通过定时器驱动执行过程，并结合 `/joint_states` 反馈进行状态判断。

当前已经实现的控制执行机制包括：

- 固定频率执行轨迹点。
- 根据规划轨迹推导控制下发节拍。
- 发布控制命令给机器人接口层。
- 根据目标关节误差判断是否到位。
- 检测关节状态反馈超时。
- 检测任务执行超时。
- 执行完成或失败时发布事件给 system manager。

这说明系统已经不只是完成静态架构搭建，而是具备了一定的闭环执行和异常保护能力。

### 9. 机器人接口适配模块已经实现

`robot_interface_pkg` 已经完成上层控制命令到 Gazebo/ros2_control 控制器指令的转换。当前系统将 `/joint_cmd` 转换为 `trajectory_msgs/JointTrajectory`，并发布到 `/joint_trajectory_controller/joint_trajectory`。

该模块的作用是屏蔽上层系统与底层仿真控制器之间的接口差异，使规划层和控制层不需要直接依赖 Gazebo 控制器的具体实现。后续如果更换仿真模型或对接真实机器人，也可以优先在接口层进行适配，降低其他模块修改成本。

### 10. 系统状态管理模块已经实现

`system_manager_pkg` 已经实现任务状态和系统状态管理。系统采用“事件流 + 正式状态流”的设计：

- 业务节点发布 `/motion_event`，表示某个模块发生了某类事件。
- system manager 根据事件和状态机规则发布 `/task_state` 和 `/system_state`。

当前任务状态包括：

- `accepted`
- `planning`
- `executing`
- `completed`
- `canceled`
- `failed`
- `rejected`

当前系统状态包括：

- `init`
- `idle`
- `busy`
- `resetting`
- `error`

状态机已经对任务流转进行约束，例如正常链路为 `accepted -> planning -> executing -> completed`，异常链路可以进入 `failed`、`canceled` 或 `rejected`。此外，系统还提供 `/reset_system` 服务，用于在测试或异常情况下复位系统状态。

## 四、存在的问题及解决方案

### 1. ROS2 与 Gazebo 环境依赖较多，启动顺序容易影响测试结果

存在问题：

ROS2、Gazebo、UR5 仿真包和本项目工作空间之间存在环境依赖关系。测试时需要先加载仿真工作空间，再加载本项目工作空间，并保证 Gazebo 控制器、`/joint_states` 和系统节点都正常启动。如果启动顺序错误，可能出现找不到 launch 文件、控制器未激活、关节状态未发布、运动任务无法执行等问题。

解决方案：

- 编写并整理统一测试执行说明，明确环境加载顺序和启动命令。
- 使用 `bringup.launch.py` 作为系统统一入口，减少手动启动多个节点的复杂度。
- 在测试前增加检查步骤，例如检查 `/joint_states` 是否发布、`joint_trajectory_controller` 是否为 active。
- 在脚本中封装常用测试命令，降低重复输入命令带来的错误概率。
- 后续继续完善启动前检查逻辑，使系统能够在关键依赖缺失时给出更明确的提示。

### 2. 多节点系统状态容易不一致

存在问题：

ROS2 系统由多个节点协同完成任务，如果每个节点都直接发布自己的状态，容易导致状态语义分散。例如规划模块认为任务已经完成规划，控制模块认为正在执行，入口模块又需要向 Action 客户端反馈状态。如果没有统一状态管理，系统对外表现会不一致，也不利于论文中说明任务生命周期。

解决方案：

- 引入 `system_manager_pkg` 作为统一状态管理模块。
- 采用“事件流 + 正式状态流”机制，各业务节点只上报 `/motion_event`，正式状态由 system manager 统一发布。
- 设计任务状态机，约束合法状态流转。
- 使用统一常量定义状态名、事件名和模块名，减少硬编码字符串不一致问题。
- 后续继续补充状态机测试，验证异常事件、重复事件和非法状态跳转是否能被正确处理。

### 3. 任务并发与抢占处理复杂

存在问题：

工业机器人运动任务具有连续性和安全性要求。如果系统同时接收多个运动任务，可能出现多个任务争用控制器、轨迹被覆盖、状态难以收敛等问题。完整实现任务抢占需要处理旧任务取消、新任务接管、控制器停止、状态回滚等细节，复杂度较高。

解决方案：

- 当前阶段采用单任务串行策略，即系统同一时间只允许一个活动任务。
- 当已有任务正在执行时，新任务直接拒绝，保证系统行为确定。
- 在接口中保留 `enable_preempt` 等扩展点，为后续扩展抢占机制预留空间。
- 论文中将该策略说明为“面向系统稳定性验证的保守设计”，并说明后续可扩展为任务队列或抢占式调度。

### 4. 速度缩放参数的端到端语义仍需进一步统一

存在问题：

当前 `speed_scale` 已经在规划层影响轨迹总时长，控制层也会按轨迹 `time_from_start` 等待发布控制点。接口层仍通过 `point_interval_sec` 适配单点 JointTrajectory。也就是说，速度缩放已影响规划与执行节拍，但仍不能写成底层控制器真实速度百分比。

解决方案：

- 在接口文档和论文中明确 `speed_scale` 当前语义：它影响规划轨迹总时长、轨迹点时间分布和控制层发布节奏。
- 在测试中设置标准速度和慢速任务，对比轨迹时间和执行过程，验证速度缩放是否体现。
- 后续可进一步统一控制层与接口层参数命名，使速度相关参数更清晰。
- 如时间允许，可增加更直观的速度统计指标，例如任务总耗时、平均关节速度和最大关节速度。

### 5. 多层超时机制边界需要进一步明确

存在问题：

当前系统中存在多层超时逻辑，包括 Action 等待结果超时、控制执行超时、关节状态反馈超时和 system manager 事件停滞 watchdog。这些机制能够提高系统异常保护能力，但如果文档说明不清楚，容易造成参数含义混淆。

解决方案：

- 对超时机制进行分层说明：入口层关注客户端等待结果，控制层关注执行过程，manager 关注任务整体生命周期。
- 在参数文档中说明各超时参数的推荐配置关系。
- 通过专门的超时测试用例验证异常链路，例如设置很小的 `timeout_sec`，观察任务是否进入 `failed`。
- 后续在论文中将超时机制作为系统可靠性设计的一部分进行说明。

### 6. 当前规划算法较简单，运动效果仍有优化空间

存在问题：

当前规划器采用关节空间线性插值方法，优点是实现简单、易于验证，但没有考虑复杂路径约束、速度连续性、加速度限制、避障和动力学约束。因此运动效果和工程实用性与成熟工业机器人规划系统相比仍有差距。

解决方案：

- 中期阶段继续保留线性插值规划，确保主链路稳定可靠。
- 在论文中明确该算法定位为“用于系统架构验证的基础规划方法”。
- 后续如时间允许，可增加速度限制、轨迹平滑或更多目标点测试。
- 将复杂规划算法作为系统可扩展方向，而不是当前阶段必须完成的核心任务。

### 7. 实验数据和结果分析还不充分

存在问题：

目前系统已经具备运行和测试能力，但实验验证还没有形成系统化结果。实验记录、rosbag 数据、截图、关键 topic 输出、成功率统计、误差分析等内容还需要进一步补充。如果实验材料不足，会影响论文中“系统验证”章节的完整性。

解决方案：

- 制定固定实验矩阵，包括正常任务、不同目标关节角任务、慢速任务、非法输入任务、超时任务和 reset 任务。
- 使用 rosbag 记录 `/joint_states`、`/planned_traj`、`/joint_cmd`、`/task_state`、`/system_state` 和 `/motion_event`。
- 每组实验记录启动命令、输入参数、系统状态流转、最终结果和异常现象。
- 对任务耗时、是否成功、最终误差、状态流转是否符合预期进行统计。
- 将实验数据整理为表格和图表，作为论文和答辩材料。

### 8. 论文撰写需要与代码实现保持一致

存在问题：

项目在开发过程中不断调整架构和实现方式，如果论文描述沿用早期设想，可能与当前代码事实不一致。例如状态管理已经从简单状态发布演化为事件流与正式状态流分离，控制层也已经加入反馈超时和执行超时机制。若文档不同步，会降低论文可信度。

解决方案：

- 以当前代码实现为准，持续同步架构文档、接口文档和进度文档。
- 论文撰写时优先引用当前已经实现并验证的功能。
- 对尚未完成的功能明确写为“后续改进方向”，不作为已完成成果描述。
- 在论文中用系统架构图、数据流图、状态机图辅助说明，使实现逻辑更清晰。

## 五、下一阶段具体工作内容

### 1. 完成系统化仿真实验验证

下一阶段首先要完成阶段 4 的系统化仿真验证。计划围绕系统主链路、状态链路和异常处理能力设计多组实验。

具体实验内容包括：

- 正常运动任务实验：验证系统能否完成 `accepted -> planning -> executing -> completed` 的完整流程。
- 不同目标关节角实验：验证系统对不同合法目标输入的适应能力。
- 慢速任务实验：验证 `speed_scale` 对轨迹时间和执行过程的影响。
- 非法输入实验：验证关节名称数量与目标位置数量不一致时系统是否拒绝任务。
- 执行超时实验：验证任务超时时是否进入 `failed` 状态。
- reset 实验：验证系统复位服务是否能正确清理活动任务并恢复到 `idle`。
- 重复执行实验：多次执行同一任务，观察系统稳定性和状态流转一致性。

每组实验需要记录：

- 实验目的。
- 启动命令。
- 输入参数。
- 关键 topic 输出。
- Action 返回结果。
- `/task_state` 状态变化。
- `/system_state` 状态变化。
- 是否出现异常。
- 最终结论。
